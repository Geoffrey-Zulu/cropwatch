# Build Phytos for iPhone

The iPhone application packages `apps/capture` with Capacitor 8. It reuses the existing farmer reporting/result/history/area-alert screens, Firebase anonymous identity and REST v1 contract. Camera/photo-library selection and location use native plugins on iOS. The web version keeps its browser implementations.

App display name: **Phytos**. Configured bundle identifier: **`zm.cropwatch.app`**. Register that identifier in your Apple team, or change it consistently in `capacitor.config.ts`, Xcode, the build script and the provisioning profile before signing. This source configuration does not reserve an identifier with Apple.

## GitHub build

Repository: `germansniper3/cropwatch`. Branch: `cropwatch-audit-ios` (based on upstream D9, not the older template on upstream `main`).

1. Open **Actions → Build Phytos iOS → Run workflow** on this branch.
2. Choose **simulator** first. It requires no Apple secrets and exports `Phytos-simulator.zip`, containing an `.app` for an iOS simulator on a Mac. It cannot be installed on a physical iPhone.
3. For a signed IPA, add repository Actions secrets and select the appropriate signing mode below. Download the `Phytos-iOS-…` artifact after the build succeeds.

To get the iPhone package before adding signing credentials, choose **unsigned-ipa**. This builds the Release app for physical iOS devices and packages it as `Phytos-unsigned.ipa`. It requires no secrets, but **must be signed before it can be installed on an iPhone**. It is not the simulator app and is not a ready-to-install distribution build.

| Secret                         | Required value                                                                                               |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| `IOS_CERTIFICATE_P12_BASE64`   | Base64-encoded Apple Distribution certificate **including its private key**, exported as `.p12`              |
| `IOS_CERTIFICATE_PASSWORD`     | Password used when exporting the `.p12`                                                                      |
| `IOS_PROVISION_PROFILE_BASE64` | Base64-encoded distribution provisioning profile for `zm.cropwatch.app`, issued to the same team/certificate |
| `IOS_TEAM_ID`                  | Apple Developer team identifier                                                                              |

**app-store-connect:** use an App Store distribution profile. The artifact is for upload to App Store Connect/TestFlight; it is not directly installable as an arbitrary download. This workflow exports the IPA but does not upload or publish it.

**release-testing:** use an ad hoc distribution profile that includes the test iPhones' registered device identifiers. This exports an IPA for those devices. Supplying a profile of the wrong type or an expired certificate will fail the Xcode export; the mode does not change the entitlements in your profile.

The workflow creates a temporary keychain, imports signing assets, validates team/bundle identity, archives and exports, then removes the imported profile/keychain. Certificate files and profiles are never committed or uploaded as artifacts. Do not paste signing secrets into a chat or commit them to Git.

## Local development

Use Node 24.15.0 or newer and the pinned `pnpm@12.9.1` CLI distributed through npm. If the Windows standalone pnpm launcher cannot find `@pnpm/win-x64`, run `npx --yes pnpm@12.9.1` instead of `pnpm`.

```bash
pnpm install --frozen-lockfile
pnpm --filter capture ios:sync
node scripts/configure-ios.mjs
pnpm --filter capture ios:open
```

The checked-in Xcode project is under `apps/capture/ios/App`. Generated web assets/config are ignored and regenerated by `cap sync`. To recreate a missing native project, run `pnpm --filter capture ios:add`, then the sync/configure commands above.

On a Mac with a supported Xcode, `bash scripts/build-ios.sh simulator` runs the same simulator build as CI. Physical-device/archive builds require signing. [Capacitor's iOS guide](https://capacitorjs.com/docs/ios) describes the Mac/Xcode tooling; [Apple's distribution guide](https://developer.apple.com/documentation/Xcode/preparing-your-app-for-distribution) explains team/signing requirements.

## What works and what remains

- The app ships its web interface inside the native bundle. It does not load the entire interface from a hosted URL, and uses HTTPS for Firebase/Cloud Run services.
- Native camera/gallery and foreground GPS connect to the existing resize/upload/report flow. Permission denial falls back to the existing district selection path; the audit documents the spatial-clustering limitation of that fallback.
- Browser service-worker registration is skipped on native. Web push is marked unsupported on native, rather than waiting forever for a service worker. Area alerts still appear inside the app through Firestore when it is opened. **Background native push is not implemented.** It needs an APNs/FCM integration and Firebase iOS app configuration; an Android or web Firebase config is not that configuration.
- Firebase JS Auth/Firestore/Storage remain the existing SDK path. Native REST requests use Capacitor HTTP and preserve the Firebase bearer token. No GCP deployment or CORS change was made for this fork.
- The default backend still belongs to `crop-watch01`. To use a different backend, provide the matching `VITE_API_URL` (including `/api/v1`) and replace the Firebase client configuration before building. Merely forking GitHub does not clone cloud data or permissions.
- The source app has no durable offline submission queue yet. Previously synchronised reports can be cached; unsent draft recovery is not guaranteed.
- Test real-device camera, gallery, permission denial, GPS denial, login persistence after relaunch, upload/retry and result/alert refresh before distributing. A simulator compile cannot validate camera hardware or provider delivery.
- Add a production privacy/consent/account-deletion flow and review dependency privacy manifests/App Store privacy declarations before App Store submission. A buildable wrapper does not guarantee App Review acceptance.
